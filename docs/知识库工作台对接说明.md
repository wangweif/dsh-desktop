# 知识库工作台对接说明

> 2026-10-12 落地，同日由**直连 RAGFlow 切换为 agent_platform 中转**。内置「知识库
> 问答」工作台（`dsh-workbench-knowledge`）经平台代访农科小智统一知识库（RAGFlow），
> 提供选库 + 流式问答（含参考文档）。RAGFlow 接口规范见飞书 wiki《农科小智知识库接口》
> （`SJOZwkIWAiewhsk1Wpbc1Hn4nUb`）；平台侧端点在 agent_platform
> `routers/workbench_knowledge.py`（commit `5a5f2e6`）。

## 功能与流程

```
面板（右侧业务区）            宿主半 loopback              agent_platform（中转）         RAGFlow
  ├─ GET /api/workbench-knowledge/datasets
  │      └─ nongkeEnterprise.apiGet ──────> GET /api/workbench/knowledge/datasets
  │          （登录态 cookie，10s 超时）        └─ GET /api/v1/datasets ───────> 知识库列表
  │                                             （平台持 key，会话鉴权）
  └─ POST /api/workbench-knowledge/ask
         {question, datasetIds} ── nongkeEnterprise.apiStream ──> POST /api/workbench/knowledge/ask
             （120s 超时 + 断开联动中止）          {question, dataset_ids}
                                                  └─ POST /api/v1/sessions/ask ──> SSE 流式回答
                                                  （逐块透传，SSE 三头同 ws.py）
```

- **鉴权链**：桌面登录（借道 agent_platform SSO）→ 交接文件 → 宿主半
  `nongkeEnterprise` 服务每请求现读会话 cookie 调平台；平台端点走
  `get_current_user`（登录用户即可，与直连时期等权——全部 dataset 可见）。
  cookie 不出宿主进程，RAGFlow key 只存在平台 `.env`。
- **流式链路**：平台把 RAGFlow SSE 响应体逐块透传（客户端断开由 Starlette 取消
  生成器、finally 关上游）；宿主半 loopback 桥再逐块透传；客户端
  `response.body.getReader()` 逐行解析 `data:` 帧。**`answer` 为累积快照**——每帧
  都是到当前为止的完整文本（2026-10-14 内网实测；官方接口示例按增量拼接是错的，
  照抄会把累计文本反复追加成灾难性重复），客户端按整体替换渲染；思考模型把推理
  过程包在 answer 开头的 `<think>…</think>` 里，面板渲染时剥离、思考期间显示
  「回答中…」占位。`reference.chunks` 为参考文档、`data: true` 结束、
  `code!==0` 报错。
- **面板**：知识库下拉 + 问答消息列表（问题气泡、流式回答、参考文档及相似度）
  + 输入行（Enter 提问，输入法组词中不误触发）。加载失败展示宿主半给出的具体
  原因（如「请先登录农科小智账号」「无法连接农科小智平台」）。原生会话仍在左侧。

## 配置

**桌面端无任何直连配置**——`build/dsh-desktop.patch.yml` 的
`dsh-workbench-knowledge` 条目只有 id/name；目标平台随登录态（交接文件里的
serverUrl）自动确定。RAGFlow 地址与 key 只在 agent_platform `.env`
（`RAGFLOW_BASE_URL` / `RAGFLOW_API_KEY`）维护，**轮换 key 不再需要重发桌面安装包**。

部署要求：agent_platform 服务器需 ≥ commit `5a5f2e6`（含
`routers/workbench_knowledge.py`），且服务器可达内网 RAGFlow
（192.168.8.88:9380）。

## 包与登记

- `packages/dsh-workbench-knowledge/`：`index.js` 宿主半（2 条 loopback 路由，
  `inject: ['connection', 'nongkeEnterprise']`，包络约定与
  `dsh-workbench-internal` 一致：业务结果 HTTP 200 `{ok,…}`、畸形请求 400）、
  `client.js` 客户端半（`desktopWorkbenches.register`，
  `layout: { businessSide: 'right', businessWidth: 0.38 }`）。
- `packages/dsh-enterprise-agents/`：`nongkeEnterprise` 服务新增
  `apiStream(path, init)`——与 `apiGet/apiPost` 同一 cookie/401 语义，但不解析
  包络、不强制超时（调用方经 `init.signal` 控制），返回原始 `Response` 供逐块
  消费；未登录一律 `unauthorized` 短路。
- 登记：根 `package.json` `file:packages/dsh-workbench-knowledge` +
  `build/dsh-desktop.patch.yml` insert（置于 dsh-workbench-internal 之前）+
  **dsh closure patch**（`patches/@deepseek-ai+dsh+0.2.0-rc.2.patch` 的
  package.json hunk 必须含该条目，`test/desktop-plugin-closure.test.ts` 据此把关）。
- 测试：`test/workbench-knowledge-routes.test.ts`（注册契约、服务依赖、包络
  映射、SSE 透传、错误边界；`nongkeEnterprise` 用桩服务）+
  `test/nongke-enterprise-service.test.ts`（apiStream 契约：cookie 携带、init
  透传、401/网络失败映射）。

## 顺序说明（「排在内部系统上面」）

- 全新安装：内置工作台首次引入顺序跟随插件加载顺序，patch 中已把 knowledge
  置于 internal 之前；实际显示顺序以内网实测为准。
- **已部署用户**：容器 `reconcileLocalProviders` 把新工作台 append 到 `pinned`
  尾部，默认排在「内部系统」之后；在「工作台管理」界面把它拖到顶部一次即可
  （容器已支持 reorder，未为此改动容器通用逻辑）。
